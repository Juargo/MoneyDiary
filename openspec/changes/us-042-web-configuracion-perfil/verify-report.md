## Issues

### CRITICAL-1 — WCFG-08's dialog-blocking scenario is unimplemented
`Vincular con Google` and `Desvincular` can be confirmed with an empty `Password actual`. The confirm button is only `disabled={pendiente}`; the password `CampoTexto` has no `required`; `ConfirmarPasswordDialog.enviar()` and `GoogleVinculoSection.confirmar()` perform no empty-string check before calling `vincular.mutate('')` / `desvincular.mutate('')`. This sends a request to the server with a known-empty authorization credential instead of blocking client-side as WCFG-08 scenario 2 requires ("THEN the confirm action is blocked until a value is entered"). No test exercises this path. The server will presumably reject it (403/400), so there is no account-takeover risk, but the spec's explicit client-side contract is unmet and untested — this is squarely in the WCFG-08 "authorisation input" requirement the task instructions asked to scrutinize.
**Fix scope**: add a client-side guard (e.g., disable `Confirmar` while `passwordActual.trim() === ''`, or an early return in `confirmar()`/`enviar()`) plus a regression test per dialog (or a shared one parametrized over vincular/desvincular). Small, isolated change — does not require reopening the sequential-save orchestration.
**Blocks archive**: yes, per the Decision Gates table ("Spec scenario has no passing covering test → CRITICAL").

### WARNING-1 — WCFG-03's literal text says "link... mutation MUST invalidate ['auth-me']"; `useVincularGoogle` does not
`useVincularGoogle` (`use-google-vinculo.ts:24-34`) never calls `invalidateQueries`. This is a **documented** divergence (in-code comment + design.md §1/Q6c): the link flow is a full external OAuth redirect via `window.location.assign`, so the SPA's query cache is irrelevant — the browser leaves the page entirely, and `_authenticated.tsx`'s `beforeLoad` re-primes identity fresh on the return leg. Functionally this achieves the same end state (fresh identity after linking) via a mechanism that avoids a wasted round trip, and it is exercised by `GoogleVinculoSection.test.tsx`'s "vincular con éxito navega vía window.location.assign" test. The spec's summary sentence, read literally, is slightly broader than what was implemented; the two per-outcome scenarios given for WCFG-03 do not actually name "link" specifically, so this reads as an unresolved textual gap in the spec rather than a functional defect. Recommend tightening WCFG-03's wording in a future spec revision to say "profile, password, or unlink" (or explicitly carve out the link's full-navigation exception) so the requirement text matches the intentional design.
