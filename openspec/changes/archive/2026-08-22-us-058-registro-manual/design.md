## 1. Overview + Design Principles

Add ONE writer endpoint, `POST /api/movimientos`, that registers a single hand-typed movement with no
cartola. `GET /api/movimientos` already exists (`movimientos.routes.ts:19`); this is a natural REST
extension on the same route module. Type-first: **Ingreso** auto-classifies by construction
(`{abono>0, cargo=0, bucket=Ingreso, categoriaId=null}`); **Gasto** validates a `(bucket, categoriaId)`
cascade against the caller's own catalog (ADR-036/037), reusing the exact US-057 machinery.

```
POST /api/movimientos   (authenticated + x-api-key)
  └─ routes/movimientos.routes.ts :: registrarMovimientoManual (NEW handler; GET stays)
       │   express.json() body → registrarMovimientoManualSchema.safeParse (TRANSPORT SHAPE ONLY)
       │   shape fail ⇒ 400 scrubbed (no raw body echo)
       └─ RegistrarMovimientoManualUseCase.execute({userId, tipo, fecha, descripcion, monto, bucket?, categoriaId?})
            ├─ 1. build MovimientoManual VO (domain)      → type/money/overflow/fecha≤today invariants (Result)
            ├─ 2. IRegistrarMovimientoManualWriter.asegurarCuentaManual(userId) → {accountId}   ←WRITE (idempotent sentinel)
            │        (NOT IAccountRepository.ensure — 'Manual' does not type-fit DetectedBank; see D-05)
            ├─ 3. GASTO ONLY: ICategoriaRepository.listarConPatrones(userId)  (READ; fail-closed)
            │        build Set<categoriaId> (membership) + Map<categoriaId,Bucket> (bucket-match)
            │        categoriaId ∉ Set ⇒ CategoriaFueraDeCatalogoError (400)
            │        Map.get(categoriaId) ≠ bucket ⇒ BucketCategoriaNoConcuerdaError (400, NEW)
            ├─ 4. resolve final { bucket: Bucket, categoriaId: string|null }:
            │        Ingreso ⇒ { Bucket.Ingreso, null } BY CONSTRUCTION (CategorizarTransaccionUseCase NOT invoked)
            │        Gasto   ⇒ { <requested bucket>, categoriaId }
            └─ 5. IRegistrarMovimientoManualWriter.registrar({userId, accountId, transaccion, bucket, categoriaId})
                     ←WRITE (single Transaccion.create, ingestaId=null, origen='Manual', descripcion encrypted)
       └─ aRegistrarMovimientoManualResponseDto(...)   (infra; BigInt→string)  → 201
```

Design principles (ADR-005/011/013/015/024): dependency rule untouched (`domain ← application ←
infrastructure`); `Result<T,E>` never throws in domain/application; Spanish naming in
domain/application, English in infra; money stays `bigint` internally, emitted as BigInt-safe strings
at the boundary; amounts scrubbed from every error message; every WHERE scoped by `userId`
(RNF-SEC-006); strict TDD (ADR-016), domain → application → infrastructure. `web`/`mobile` untouched
(forms are US-060/061). ONE migration (nullable relax + `origen` column + optional CHECK).

## 2. The 4 open questions — RESOLVED

| # | Question | RESOLUTION | Rationale (code-verified) |
|---|----------|-----------|---------------------------|
| **1** | `origen` shape: `String?` null=ingesta (C-a) vs `String NOT NULL` backfilled `'Ingesta'` (C-b) | **C-a: `origen String?`, `null` = ingesta-born, `'Manual'` = manual.** | `Transaccion` is the largest table; C-b forces an `UPDATE` over every existing row for zero product gain. The pairing invariant makes `null` unambiguous: `ingestaId` is non-null exactly for ingesta rows, so `origen IS NULL ⇔ ingestaId IS NOT NULL ⇔ ingesta-born`. Query ergonomics for the sole future consumer ("show my manual entries") are identical: `WHERE origen = 'Manual'` works under both; no index is added (YAGNI — no query requires it this sprint, and the `@@index([accountId, fecha])` at `schema.prisma:208` already serves the money readers). Matches the additive-column posture of `duplicadosOmitidos` (`schema.prisma:107-111`, `@default(0)`, no data backfill). |
| **2** | Raw-SQL CHECK `(ingestaId IS NULL) = (origen = 'Manual')` vs single-writer only | **ADD the raw-SQL CHECK** `Transaccion_origen_ingesta_consistency`. | Repo precedent is unambiguous: two CHECKs already exist via raw SQL because Prisma can't model them — `Transaccion_cargo_abono_no_negativos` (`20260710185710`) and `Ingesta_procesada_requires_account` (`20260801000000:54-55`). The `origen`/`ingestaId` pairing is the exact same class of data-layer invariant (defense-in-depth on top of the single-writer guarantee), and it is CHEAP (one constraint, no runtime cost). It closes the "two origin sources drift" risk at the data layer: a future non-manual writer that forgets `origen` would be rejected by the DB, not silently corrupt provenance. This is NOT over-engineering — it is the house pattern for money-adjacent invariants (ADR-015 concentrates rigor on the money path). |
| **3** | Ingreso carrying stray `bucket`/`categoriaId`: strict 400 vs silently ignore | **STRICT 400 via the DTO schema (discriminated union).** | The repo's boundary doctrine is fail-closed for *malformed requests* (catalogo `.safeParse` → scrubbed 400, `movimientos.schema.ts` layer-honesty). US-057's advisory-overlay doctrine (D-11 "Ingreso overlay silently ignored") applies to a *batch re-classification overlay* where dropping a stray edit is a no-op on an already-parsed file — a different situation. Here the request IS the movement: an Ingreso body carrying `bucket`/`categoriaId` signals a CLIENT BUG or a wrong `tipo`, and silently ignoring it would let a caller believe they classified an income. A Zod **discriminated union on `tipo`** (`z.discriminatedUnion('tipo', [ingresoSchema.strict(), gastoSchema])`) makes `bucket`/`categoriaId` **unknown keys on the Ingreso variant** → `.strict()` rejects them at the transport boundary with a scrubbed 400, before the use case runs. One doctrine, chosen: **fail-closed on a malformed request**, consistent with every other write endpoint in the repo. |
| **4** | Writer input: reuse `TransaccionAPersistir` vs dedicated `MovimientoManualAPersistir` | **Dedicated narrow port `IRegistrarMovimientoManualWriter`; do NOT reuse `TransaccionAPersistir`/`IIngestaRepository`.** The writer input carries a built `Transaccion` VO + `bucket: Bucket` + `categoriaId`. | `TransaccionAPersistir` (`ingesta-repository.port.ts:21-27`) is `{ transaccion, bucket: Bucket\|null, categoriaId }` — structurally it fits, BUT it is threaded through the *ingesta batch* chain (`PersistTransactionsUseCase → IIngestaRepository.persistirProcesada` writes an `Ingesta` row + `createMany`, `prisma-ingesta.repository.ts:39-61`). Reusing that path would FABRICATE a fake `Ingesta` — the exact semantic corruption ADR-026 forbids and the proposal rejects (§Scope). ISP says the manual writer needs a single-row `Transaccion.create` with `ingestaId=null`, which no existing port exposes. **The manual flow DOES build a `Transaccion` VO** (for the money/overflow/XOR invariants — `Transaccion.crear`, `transaccion.ts:39-58`), so the writer's input reuses the `Transaccion` VO + the domain `Bucket` enum, and the adapter resolves `bucket → BUCKET_IDS[bucket]` the same way `aPersistencia` does (DRY on FK resolution, D-08). Net: reuse the VO and the FK-resolution technique, NOT the batch port. |

## 3. Decisions (ADR-style)

| id | decision | rationale | rejected alternative |
|----|----------|-----------|----------------------|
| **D-01** | **Domain: a new `MovimientoManual` factory VO wraps the existing `Transaccion` VO — it does NOT re-implement money validation.** `MovimientoManual.crear({ tipo, fecha, descripcion, monto: string, clock? })` (Spanish, `domain/value-objects/movimiento-manual.ts`) returns `Result<MovimientoManual, MovimientoManualInvalidoError>`. Ownership of the `monto` input chain is explicit: (a) `MovimientoManual.crear` OWNS the decimal-string → `bigint` conversion and the overflow guard: it rejects non-numeric strings, negative values, zero, and string magnitudes whose numeric value exceeds `Number.MAX_SAFE_INTEGER` — this guard is NEWLY ESTABLISHED here (no exact repo precedent; the closest prior art is the Excel normalizer's `parseInt`+`isFinite` chain, which is weaker and does not cover the `Number.MAX_SAFE_INTEGER` boundary; `transaccion.mapper.ts` is a `bigint→bigint` passthrough with no such guard) — emitting `MONTO_INVALIDO` or `MONTO_OVERFLOW` as appropriate; (b) after conversion, it maps `tipo` → `(cargo, abono)`: `Ingreso ⇒ {cargo:0n, abono:monto}`, `Gasto ⇒ {cargo:monto, abono:0n}`, then delegates to `Transaccion.crear(...)` for the XOR/non-negative/non-zero invariants (`transaccion.ts:47-55`); `Transaccion.crear` does NOT validate overflow — its inputs are already `bigint` values and it has no `Number.MAX_SAFE_INTEGER` guard (verified: `transaccion.ts:39-58`); (c) validates `descripcion` trimmed non-empty and ≤ 500 characters, emitting `DESCRIPCION_VACIA` or `DESCRIPCION_LARGA` respectively — **explicit design decision:** 500 chars chosen as a sensible UX cap — no existing repo precedent for a descripcion max; this is an explicit new decision with no prior art to mirror; revisit trigger: a real user need for longer notes; `Transaccion.crear` does NOT validate `descripcion` (verified: `transaccion.ts:39-58` — it accepts the string as-is); (d) enforces **`fecha ≤ today` IN THE DOMAIN** (future ⇒ `FECHA_FUTURA`). `MovimientoManual.crear` fails with a `MovimientoManualInvalidoError` whose code enum is `FECHA_FUTURA \| DESCRIPCION_VACIA \| DESCRIPCION_LARGA \| MONTO_INVALIDO \| MONTO_OVERFLOW`. `Transaccion.crear` failures (`SIN_MONTOS`/`MONTO_NEGATIVO`/`CARGO_Y_ABONO`) are mapped into `MovimientoManualInvalidoError` at the VO boundary — the manual flow surfaces a single domain error type. `MovimientoManual` exposes `.transaccion` (the built `Transaccion`), `.tipo`, and `.esIngreso()`. | Money exactness and the débito-XOR-crédito invariant already live in `Transaccion.crear` (single source, DRY skill). `MovimientoManual.crear` owns the upstream conversion + overflow guard because `Transaccion.crear` takes `bigint` inputs — there is no guard there to delegate to for overflow. The VO is the KISS "boring technology" choice — same VO+factory+`Result` pattern the repo uses everywhere. `descripcion` non-empty and length capping is a business rule owned by this new input surface; `Transaccion.crear` was never the owner. Placing `fecha ≤ today` in the domain (not the DTO) keeps it a business rule with a domain error, testable without HTTP (ADR-005). | (a) Claiming overflow delegation flows through `Transaccion.crear` — it does not; `Transaccion.crear` has no overflow guard (verified `transaccion.ts:39-58`). (b) Putting `fecha ≤ today` in the Zod schema — leaks a business rule into transport. (c) Skipping the VO and passing raw fields to the writer — no invariant enforcement, breaks the money-safety doctrine. |
| **D-02** | **`fecha ≤ today` comparison boundary: compare on the UTC calendar date, `today` inclusive; "future" = strictly after today's date in UTC.** `MovimientoManual.crear` receives `fecha: Date` (already parsed from the ISO `YYYY-MM-DD` string at the DTO boundary) and a clock. It rejects when `fecha`'s UTC date > `now`'s UTC date. Unlimited past (backfill), today allowed. | Proposal CA-01 pins "past or today only, unlimited backfill". Comparing calendar dates in UTC (not instants) avoids a timezone-of-server foot-gun where "today" typed by a user in Chile is rejected as future. `Transaccion.fecha` is already UTC-normalized (`transaccion.ts:8`), so the VO stays consistent. The clock is injected (a `() => Date` or `Clock` param) so the rule is deterministically testable — same discipline `PeriodoMes.actual()` implies. | Comparing full instants (`fecha > new Date()`) — rejects a today-dated movement typed a few hours "ahead" in local time; and is non-deterministic in tests. Hardcoding `new Date()` inside the VO — untestable, forbidden by the strict-TDD posture. |
| **D-03** | **New domain error `BucketCategoriaNoConcuerdaError` (Gasto: categoría exists in the caller catalog but its bucket ≠ the requested bucket).** Fixed compile-time message, NO interpolation of `categoriaId`/`bucket`/amounts (ADR-013) — mirrors `CategoriaFueraDeCatalogoError` (`categoria-fuera-de-catalogo.error.ts:19-27`) exactly. The rejected `categoriaId`/`bucket` are kept as public props for logging, never reach `.message`. Maps to **400**. | The cascade has TWO distinct failure modes (proposal CA-03): categoría outside the catalog (reuse `CategoriaFueraDeCatalogoError`) vs categoría inside but bucket-mismatched (NEW). They are different knowledge and must be distinguishable errors (DRY rule 1: distinct rules stay separate). The fixed-message doctrine is the established scrub-safe pattern for catalog errors. | A single generic "categoría inválida" error — loses the diagnostic distinction the two CA-03 sub-cases require. Interpolating the bucket/categoriaId into the message — ADR-013 scrub violation. |
| **D-04** | **New narrow persistence port `IRegistrarMovimientoManualWriter` (application/ports/) with TWO methods** (resolving open Q4): `asegurarCuentaManual(userId): Promise<Result<{ accountId: string }, PersistenciaFallidaError>>` and `registrar(input: RegistrarMovimientoManualInput): Promise<Result<{ id: string }, PersistenciaFallidaError>>`, where `RegistrarMovimientoManualInput = { userId; accountId; transaccion: Transaccion; bucket: Bucket; categoriaId: string | null }`. It does **not** reuse `TransaccionAPersistir` nor `IIngestaRepository`. | ISP: the manual flow needs a single-row `Transaccion.create` with `ingestaId=null` — a capability no existing port exposes. Reusing `IIngestaRepository.persistirProcesada` would fabricate a fake `Ingesta` (semantic corruption, ADR-026). The input carries the built `Transaccion` VO (already validated, D-01) + the domain `Bucket` enum; the adapter resolves `bucket → BUCKET_IDS[bucket]` (D-08). Two methods on ONE port (not two ports) because both are the single "register a manual movement" responsibility and the use case orchestrates ensure→registrar in sequence; splitting them into two ports would over-segment (KISS). `registrar` takes `bucket: Bucket` non-null because a manual movement ALWAYS has a resolved bucket (Ingreso or a chosen Gasto bucket) — no null-bucket case exists (unlike one-shot ingesta). | (a) Reuse `TransaccionAPersistir` + `PersistTransactionsUseCase` — drags batch/ingesta semantics, fabricates an `Ingesta` (open Q4). (b) Widen `IAccountRepository`/`IIngestaRepository` — widens write ports for a second consumer (ISP violation, same anti-pattern US-057 D-05 rejected). (c) Two separate ports (`IEnsureCuentaManual` + `IRegistrarMovimientoManual`) — over-segmentation; both are one adapter, one responsibility. |
| **D-05** | **Sentinel account: the manual writer's OWN idempotent upsert — NOT `IAccountRepository.ensure()`.** `asegurarCuentaManual(userId)` upserts `Account` on the SAME natural key `@@unique([userId, banco, tipoCuenta, numeroCuentaBlindIndex])` (`schema.prisma:78`) with **fixed sentinel values**: `banco='Manual'`, `tipoCuenta='Manual'`, `numeroCuenta` = `crypto.encrypt(normalizeNumeroCuenta('MANUAL'))` (the same `normalizeNumeroCuenta` call feeds the encrypt path as well as the blind-index — single-source rule from `normalize-numero-cuenta.ts:11-13`), and `numeroCuentaBlindIndex = blindIndex.compute(normalizeNumeroCuenta('MANUAL'))`. **IMPLEMENTATION CONSTRAINT:** the three raw sentinel strings (`'Manual'`, `'Manual'`, `'MANUAL'`) MUST be declared as module-level constants in `prisma-registrar-movimiento-manual.repository.ts` (e.g. `SENTINEL_BANCO = 'Manual'`, `SENTINEL_TIPO_CUENTA = 'Manual'`, `SENTINEL_NUMERO_CUENTA_RAW = 'MANUAL'`) — NEVER repeated as inline string literals. A typo in one call site would silently create a split-brain second sentinel row via the 4-field unique key, breaking per-user upsert idempotency without any compile-time or runtime warning. Additionally, the blind-index computation (`numeroCuentaBlindIndex`) MUST NOT be skipped: a `null` `numeroCuentaBlindIndex` breaks upsert matching under Postgres unique-NULL semantics — two NULL values in a unique index column are treated as distinct, so a skipped blind index would generate a new sentinel row on every call instead of hitting the existing one. Idempotent per user (upsert `where` on the composite key, `create` on miss, `update: {}` on hit — byte-identical mechanics to `prisma-account.repository.ts:44-61`). | **DECISIVE code fact:** `IAccountRepository.ensure(userId, banco: DetectedBank)` (`account-repository.port.ts:16`) requires `DetectedBank.banco: BancoConocido` (4-value enum, `nombre-banco.ts:8-13`) and `tipoCuenta: TipoCuentaConocido` (3-value enum, `tipo-cuenta.ts:6-10`). `'Manual'` is in NEITHER enum, so `ensure()` CANNOT be called with a manual sentinel without widening those domain enums — a large blast radius touching bank detection/strategies (OCP violation, and semantically wrong: 'Manual' is not a recognized bank). The manual writer therefore owns its own upsert against the raw `Account` table (`Account.banco`/`tipoCuenta` are plain `String`, `schema.prisma:65-66` — the DB accepts 'Manual'). It reuses the SAME `ICryptoService` + `IBlindIndexService` + `normalizeNumeroCuenta` (DRY on the blind-index/encryption path). Per-user isolation is structural via the composite key including `userId`. `accountId` STAYS NOT NULL on `Transaccion` — the sentinel carries it, so the `account:{userId}` isolation chain in all 5 readers is UNTOUCHED. | (a) Call `ensure()` with a cast/widened `DetectedBank` — forces 'Manual' into `BancoConocido`/`TipoCuentaConocido`, corrupting bank-detection domain enums (OCP + semantic violation). (b) Make `accountId` nullable and skip the account — breaks `account:{userId}` isolation in 5 readers (proposal approach B, high blast radius). (c) A shared "system account" not per-user — breaks RNF-SEC-006 isolation. |
| **D-06** | **US-052 Origen renders `'Manual'` with zero changes to the income reader — VERIFIED.** The Origen column derives `origen: fila.banco || 'Manual'` (`obtener-ingresos-mes.use-case.ts:55`); `fila.banco` comes from `row.account.banco` (`prisma-detalle-bucket.repository.ts:91`, `prisma-movimientos-mes.repository.ts:88`). A sentinel `banco='Manual'` feeds that path unchanged. A REQUIRED new integration test must therefore cover: a sentinel-born row ⇒ `GET /api/ingresos/mes` ⇒ `origen='Manual'` (truthy branch confirmed end-to-end). One source of truth (account join) avoids the drift risk between the account and the `origen` column. | Reading the new `origen` column in the UI derivation this sprint — introduces a second source that can drift from the account `banco` (the exact risk the proposal pins). Deferred. |
| **D-07** | **CA-05 (resumen/50-30-20/semáforo update automatically) — VERIFIED zero-work.** `PrismaResumenMesRepository` groups by `bucketId` with `where: { account: { userId }, fecha: {gte,lt} }` and NO ingesta/origen filter (`prisma-resumen-mes.repository.ts:37-40,60-62`). A manual `Transaccion` with a real `bucketId` FK, owned by the user's sentinel account, in-period, contributes to the month math BY CONSTRUCTION. The two sibling readers (`prisma-detalle-bucket`, `prisma-movimientos-mes`) filter identically. | The 50/30/20 math keys off `Transaccion.bucketId` (`groupBy(['bucketId'])`), not off ingesta or origen. Ingreso rows get `bucket=Bucket.Ingreso` → `BUCKET_IDS[Ingreso]` (a real FK, Ingreso IS one of the 5 buckets, `bucket.ts:11-16`); Gasto rows get the chosen `bucketId`. ADR-024: backend computes, client renders — no client change. | Special-casing manual rows in the readers — unnecessary and would break the "zero reader change" guarantee (CA-05). |
| **D-08** | **FK resolution `Bucket → BUCKET_IDS[bucket]` lives in the INFRASTRUCTURE adapter, never in application (ADR-005).** `PrismaRegistrarMovimientoManualRepository.registrar` resolves `BUCKET_IDS[input.bucket]` to the physical `bucketId` string before the `Transaccion.create`, and `crypto.encrypt(input.transaccion.descripcion)` for `descripcion`, exactly as `aPersistencia` does (`transaccion.mapper.ts:53-61`). The application use case builds `RegistrarMovimientoManualInput` with the DOMAIN `Bucket` enum only. **Response DTO source:** `aRegistrarMovimientoManualResponseDto` maps from the in-memory `MovimientoManual` VO (`vo.transaccion.descripcion` is the plaintext string, already in memory); there is NO DB read-back after `registrar()` and NO decrypt round-trip — the persisted `descripcion` is encrypted but the response always uses the VO's plaintext. | The port docstring (`categoria-repository.port.ts:50-53`) explicitly forbids application from resolving `BUCKET_IDS` (it lives in `infrastructure/persistence/`). Reusing that technique keeps ONE source of truth for the enum→FK mapping (DRY on a load-bearing FK). `descripcion` encryption reuses the SAME `ICryptoService` instance from the composition root (ADR-013) — no new crypto. | (a) Resolving `BUCKET_IDS` in the use case — ADR-005 layer violation, contradicts the explicit port docstring. (b) A new `IBucketIdResolver` port — unnecessary indirection; the adapter already has the knowledge. (c) Re-declaring the bucket→id map — DRY violation on a load-bearing FK. |
| **D-09** | **Use case error union + exhaustive `never` guard + outer try/catch. Manual-movement failures DO NOT register any historial entry.** `RegistrarMovimientoManualError = MovimientoManualInvalidoError \| CategoriaFueraDeCatalogoError \| BucketCategoriaNoConcuerdaError \| PersistenciaFallidaError` — this is a CLOSED set; the `never` guard at the route enforces exhaustiveness at compile time. Route mapping: the three domain errors ⇒ 400 (scrubbed); `PersistenciaFallidaError` ⇒ 500. Exhaustive `never` guard at the route (mirror `movimientos.routes.ts:46-47`). The use case wraps its body in a top-level try/catch translating any mid-flight throw into `Result.fail(PersistenciaFallidaError)` (never-throw contract, mirror `process-ingesta.use-case.ts:122-143`). How `Transaccion.crear` failures surface: `MovimientoManual.crear` maps every `TransaccionInvalidaError` code (`SIN_MONTOS`, `MONTO_NEGATIVO`, `CARGO_Y_ABONO`) into `MovimientoManualInvalidoError` at the VO boundary — the use case sees only the single domain error type `MovimientoManualInvalidoError` (closed code enum: `FECHA_FUTURA`, `DESCRIPCION_VACIA`, `DESCRIPCION_LARGA`, `MONTO_INVALIDO`, `MONTO_OVERFLOW`, `SIN_MONTOS`, `MONTO_NEGATIVO`, `CARGO_Y_ABONO`). The use-case error union is therefore `MovimientoManualInvalidoError \| CategoriaFueraDeCatalogoError \| BucketCategoriaNoConcuerdaError \| PersistenciaFallidaError` — `never` guard over that closed set. **NO FALLIDA / no `Ingesta` row is written on failure** — `Ingesta`/`EstadoIngesta.FALLIDA` is the *file-import* historial (ADR-026); a manual movement is not an ingesta, so a failed manual attempt registers nothing (there is no "manual historial" in scope — proposal §Non-goals). | The FALLIDA writer (`IRegistrarIngestaFallidaWriter`) exists to record *failed file uploads* in the `Ingesta` table. ### D-13 SQL (exact)

```sql
-- US-058: manual movements. A Transaccion may now be manual (no ingesta).
-- Two schema moves + one data-integrity CHECK, one migration.

-- 1. Relax ingestaId to nullable (US-004 relax pattern, 20260801000000:44-46).
--    Pure widening — no data change. Existing rows keep a non-null ingestaId.
--    NOTE: keep the FK onDelete pinned to Restrict (schema.prisma:185 has no
--    explicit onDelete; Prisma default for a required relation is Restrict.
--    After relaxing to optional, Prisma's default for an OPTIONAL relation is
--    SetNull — so schema.prisma MUST pin `onDelete: Restrict` explicitly on the
--    ingesta relation to avoid a drift-regenerated migration, exactly as the
--    Ingesta.account relation does at schema.prisma:100).
ALTER TABLE "Transaccion" ALTER COLUMN "ingestaId" DROP NOT NULL;

-- 2. Add origen (C-a): null = ingesta-born, 'Manual' = manual. Additive, no backfill.
ALTER TABLE "Transaccion" ADD COLUMN "origen" TEXT;

-- 3. Pairing invariant (raw SQL — Prisma can't model CHECK; same posture as
--    Transaccion_cargo_abono_no_negativos / 20260710185710 and
--    Ingesta_procesada_requires_account / 20260801000000:54-55).
--    (ingestaId IS NULL)  ⇔  (origen IS NOT DISTINCT FROM 'Manual')
--    NULL-safe form chosen because Postgres three-valued logic makes the naive
--    (ingestaId IS NULL) = (origen = 'Manual') PASS on (ingestaId=NULL, origen=NULL):
--    NULL = 'Manual' evaluates to NULL, and TRUE = NULL evaluates to NULL,
--    and a NULL CHECK result is treated as passing by Postgres.
--    IS NOT DISTINCT FROM uses null-safe equality (SQL standard), the same
--    idiom already used in this repo's CHECK precedents.
ALTER TABLE "Transaccion" ADD CONSTRAINT "Transaccion_origen_ingesta_consistency"
  CHECK (("ingestaId" IS NULL) = ("origen" IS NOT DISTINCT FROM 'Manual'));
```

**schema.prisma edits accompanying the migration:** `ingestaId String?`; `ingesta Ingesta? @relation(fields: [ingestaId], references: [id], onDelete: Restrict)` (pin `onDelete` to prevent drift, as `Ingesta.account` does); add `origen String?` with a comment documenting `null = ingesta-born, 'Manual' = manual (US-058, C-a)`. The CHECK stays out of `schema.prisma` (raw SQL only, house pattern).

**Rollback:** `origen` drops cleanly (additive). The CHECK drops cleanly. `ingestaId` can be re-tightened to NOT NULL **only after** deleting/guarding any manual rows (`WHERE ingestaId IS NULL`) — documented in the migration down step. Because manual rows are additive and isolated, practical rollback is "remove the code path, leave the nullable column".

## 4. Delete-ingesta immunity (CA-04) — VERIFIED

`PrismaEliminarIngestaRepository.eliminarConTransacciones` deletes `Transaccion WHERE { ingestaId, ingesta: { userId, estado: PROCESADA } }` (`prisma-eliminar-ingesta.repository.ts:58-64`). A manual row has `ingestaId = null`, so `WHERE ingestaId = :deletedIngestaId` can NEVER match it — SQL three-valued logic: `NULL = <any non-null cuid>` evaluates to NULL (neither TRUE nor FALSE), so the row is excluded. This is the PRIMARY and SUFFICIENT proof of delete immunity; it stands alone regardless of how Prisma generates the SQL. After the schema relaxation makes `ingesta` an optional relation, the Prisma optional-relation filter is observed to behave as an inner join (rows without an ingesta are excluded), which is consistent with the SQL NULL-equality proof — but this Prisma-level behavior is a secondary, non-load-bearing observation and has not been independently verified against the Prisma 7 source; do not rely on it as the proof. Re-run `tsc --noEmit` after migrating to verify the where-clause still type-checks (see §7 apply gate).
