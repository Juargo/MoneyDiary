# Proposal: US-056 — Mobile: páginas de detalle MES con paridad

Issue: [#290](https://github.com/Juargo/MoneyDiary/issues/290) — the FINAL US of Sprint-14. Wireframes: M1 (Detalle MES-BUCKET) / M2 (Detalle MES-INGRESOS), board `C2hidB23uiSHhf4Bt3dyPo`.

## Intent

### The problem

The mobile dashboard (US-050) already renders the 4-item donut, the 5-row legend and the annual grid — but every one of those rows is a **dead end**. The legend's binding decision 2 (`LeyendaGasto.tsx` docstring: "non-interactive, no chevrons, no navigation") shipped the summary as a read-only surface. On the web, that same chart is a **launchpad**: tap a bucket → the month's transactions for that bucket, grouped by categoría, with the meta/porcentaje and an inline reclassify; tap Ingresos → the month's income rows with their Origen. On mobile, the user who sees a skewed bucket or a fat "Sin categoría · N tx" row on their phone has nowhere to go — they cannot drill in, cannot see *which* transactions drove the number, and cannot fix a misclassification from the device where they actually live.

This US closes the web↔mobile drill-down parity gap: it turns the inert legend into navigation and builds the two detail screens (M1 bucket detail, M2 ingresos detail) the web already ships, consuming the SAME backend endpoints, porting the SAME view-models, reproducing the SAME reclassify cascade — no new backend, no new business rule, no duplicated domain logic (ADR-024).

### Why now

- **The backend and the contract are fully shipped.** `GET /api/buckets/{bucket}/detalle` (`DetalleBucketMesDto`), `GET /api/ingresos/mes` (`IngresosMesDto`) and `PATCH /api/transacciones/{id}/categoria` (`ReclasificarCategoriaDto`) are deployed and session-scoped; all three DTOs are already in `@moneydiary/api-client`. Mobile already holds a Bearer session and sends `x-api-key`. **There is no missing API** — only a missing client surface.
- **The web reference is finished and hardened.** US-051/052/053/054/055 settled `BucketDetalleMesPage`, `GrupoMovimientos`, `ReclasificarCategoriaControl`, `IngresosMesPage` and the reclassify invalidation set across several judgment-day rounds. Parity here means *porting a settled design*, not inventing one — the view-models, the "ver N más" collapse, the cross-bucket confirm copy and the read-only-ingresos rule (WDI-06) are frozen and tested.
- **US-050 just landed the dashboard shell** in this worktree, so the entry point (the legend rows) already exists — it only needs to become pressable.
- **It is the last US of the sprint**, and it depends on nothing that is not already merged.

### What success looks like

A user on the phone can tap a bucket slice/legend row and land on that bucket's month detail — header with the mes and period arrows, the `% vs meta`, expandable groups per categoría with the "Sin categoría" group highlighted, and a per-row reclassify that moves a transaction to another bucket (with a cross-bucket confirmation before it commits). Tapping the Ingresos row lands on the income detail — total, conteo, and the Origen of each row, read-only. After a reclassify, the detail screen AND the dashboard's 50/30/20 both reflect the move when the user returns. The screens say the same things, in the same words, as the web.

## What Changes

- **Legend → navigation (CA-01).** The five `LeyendaGasto` rows become `Pressable`, reversing US-050's binding decision 2 for this US. The 3 spend-bucket rows push `/bucket/[bucket]`; the "Sin categoría" row pushes `/bucket/SinCategoria?destacar=sin-categoria`; the Ingresos row pushes `/ingresos`. The `periodo` currently held as local state on `app/index.tsx` (MOB-13) is threaded down so a detail screen opens on the same month the dashboard is showing. The donut SVG stays decorative (no per-slice hit-testing on RN `Path` — the legend row IS the target); the pie's `accessibilityLabel` is unchanged (D-01).
- **Two new routes + screens.** `app/bucket/[bucket].tsx` (M1) and `app/ingresos.tsx` (M2), registered in `_layout.tsx`'s existing `<Stack.Protected>` block. Each screen owns its own `loading | error | empty | data` fetch phases (the app's per-screen pattern, `app/index.tsx`/`categoria/[id].tsx`), NOT TanStack Query — mobile has none (D-03).
- **Two view-models ported as pure TS.** `aDetalleBucketMesViewModel` and `aIngresosMesViewModel` copied near-verbatim from web into `apps/mobile/src/domain` (+ an `aFechaCorta` helper). Presentation-only (ADR-024): all label assembly, group building, `sinMeta`/`sinPorcentaje` flags, `marcaPct` values — no backend rule re-implemented (D-04).
- **A reusable RN period-selector mini component.** `SelectorPeriodoMes` (~80 LOC): `‹ mesLabel ›` with two arrow `Pressable`s, on both detail headers. This is the mobile equivalent of web's `PeriodoSelector` — mobile has none today (D-02).
- **An RN reclassify control (M1 only, CA-04).** A `Modal` + grouped list (bucket sections → that bucket's categorías), because RN has no `<select>`/`<optgroup>`. Restricted to `BUCKETS_ASIGNABLES` (the 3 spend buckets), the cross-bucket move confirmed via `Alert.alert` per the us-044 guard pattern, and the destination announced via an accessibility mechanism that survives the moved row's disappearance (D-05, D-06, D-07).
- **A mobile refresh contract on reclassify success.** A per-screen refetch of the bucket detail PLUS `solicitarRecargaResumen()` (the existing `src/api/resumen-refresh.ts` pub/sub) so the dashboard's 50/30/20 is not stale when the user navigates back — the mobile equivalent of web's TanStack-Query invalidation of `['detalle-bucket-mes', …]` + `['resumen']` + `['resumen-anual']` (D-06).
- **New fetchers.** `fetchDetalleBucketMes`, `fetchIngresosMes` (manual `fetch` + shape guard, `ApiResult<T>`, never-throw) and a thin `reclasificarCategoria()` wrapper over the existing `enviarMutacion` (`src/api/mutacion.ts`).

## Decisions pinned (user-approved)

1. **D-01 — CA-01 targets the legend ROWS, not the donut slices.** The RN donut is an SVG made of `Path` elements with no `Pressable` wrapping (US-050 shipped it decorative, `accessibilityLabel="Distribución del gasto"`). Per-slice hit-testing on RN SVG paths is disproportionate and inaccessible; the 5-row legend already sits directly beneath it and maps 1:1 to the targets. So the legend rows become the navigation surface (3 buckets → `/bucket/[bucket]`, SinCategoria → `/bucket/SinCategoria?destacar=sin-categoria`, Ingresos → `/ingresos`), each an accessible `Pressable` (`accessibilityRole="button"`, Spanish label, explicit `testID` per the us-044 repeated-component idiom). This reverses `LeyendaGasto`'s US-050 binding decision 2 **for this US only** and is the whole of CA-01. *Rejected:* adding per-`Path` `onPress` to `DistribucionPie` (RN hit-slop on arc paths is unreliable and unlabelable).

2. **D-02 — Period ARROWS on both detail screens, via a new reusable `SelectorPeriodoMes` (~80 LOC).** The user confirmed arrows are in scope. Mobile has NO `PeriodoSelector` equivalent (the dashboard uses the annual grid as its month picker, MOB-11/MOB-13 — that grid does not exist on a detail screen). A shared `‹ mesLabel ›` mini component with two arrow `Pressable`s decrements/increments the `periodo` and re-fetches; it lives once and is consumed by both M1 and M2 headers (`dry`). Period math reuses the existing `periodoActualUTC`/`anioDePeriodo`/`mesAbreviado` helpers plus a new prev/next-month pure function. *Rejected:* "back to dashboard, pick another month, drill in again" (fails the wireframe's in-header arrows and is a worse flow); an `<input type=month>`-style native picker (no RN parity, overkill for ±1 month stepping).

3. **D-03 — Manual fetch + shape-guard state machines, NOT TanStack Query.** Mobile has deliberately never adopted a query library (`app/index.tsx` precedent; us-044 D-4.2). Each detail screen runs its own `loading | error | empty | data` phases with `useState` and a `fetch`-on-mount, mirroring `categoria/[id].tsx` (route unmounts on nav away, so no `useFocusEffect` needed for the *initial* load). Read guards keep `bucket`/`origen` as plain `string` (server is the authority, ADR-024/037 — an unrecognised bucket must still render, not fail parsing). The two new fetchers follow `fetchCatalogo`'s never-throw `ApiResult<T>` discipline verbatim. *Rejected:* introducing TanStack Query for two screens (`yagni`; a whole caching/invalidation architecture for a surface that already has a working pub/sub refresh idiom).

4. **D-04 — Port the two web view-models as pure TS, near-verbatim.** `aDetalleBucketMesViewModel(dto)` → `DetalleBucketMesViewModel` (grupos array, string labels, `sinMeta`/`sinPorcentaje`/`marcaPct`) and `aIngresosMesViewModel(dto, periodo?)` → `IngresosMesViewModel` (mesLabel, conteoLabel, totalLabel, filas). These are presentation-only (ADR-024: "if it affects how money is presented → client"): they format the numbers the backend already computed and never re-derive a bucket total, a meta, or a classification. The `aFechaCorta` helper the web view-model depends on is ported/inlined as `apps/mobile/src/domain/fecha-corta.ts`. CLP amounts flow through the existing `formatearMontoCLP`/`formatearMontoConSigno` string-safe formatters — never `parseFloat`/`Number` on the BigInt-string amount (MOB-05 discipline). *Rejected:* re-fetching or re-computing any figure client-side; sharing code with web (no `packages/shared`, ADR-008 — hand-port and pin every string in a unit test so drift shows up as an intentional edit).

5. **D-05 — The RN reclassify control is a `Modal` + grouped list, restricted to `BUCKETS_ASIGNABLES`.** RN has no `<select>`/`<optgroup>` (the web cascade primitive). The highest-effort item of this US is realized as a full-screen or bottom `Modal` whose body is a grouped, scrollable list: bucket section headers (Necesidades / Gustos / Ahorro — the 3 spend buckets only, mirroring US-055 D-02) → that bucket's own categorías as rows. Tapping a categoría selects it. `Alert.alert` is **only** the binary cross-bucket confirm (per below), NOT the picker — the us-044 exploration already ruled `Alert.alert` insufficient for a full category list (≤3 buttons). Every repeated row carries an explicit `testID`; the trigger is a `Pressable` per movement row inside `GrupoMovimientosMobile`. *Rejected:* `ActionSheetIOS`/`@react-native-picker/Picker` (platform-specific, no grouped-section parity); a new bottom-sheet library (`yagni` — a `Modal` + `ScrollView` is enough).

6. **D-06 — Reclassify success refreshes the detail screen AND the dashboard, via refetch + `solicitarRecargaResumen()`.** Web invalidates `['detalle-bucket-mes', bucket, clave]`, `['resumen', clave]`, `['resumen-anual']` and (US-055 D-03) `['ingresos-mes']` on a successful reclassify. Mobile's equivalent, with no query cache: (a) the M1 screen re-runs its own `fetchDetalleBucketMes` for the current `periodo` (so the moved row leaves its old group / the "Sin categoría" destacado group empties), and (b) it fires `solicitarRecargaResumen()` (the Set-based pub/sub in `src/api/resumen-refresh.ts` already consumed by `subir.tsx` after an upload, and by us-044 MCTG-07 after a bucket change) so the dashboard's `ResumenScreen`/`ResumenAnual` refetch on their next focus. This is the pinned refresh contract: **any successful reclassify MUST both refetch the open detail and signal a dashboard resumen recarga.** The `/ingresos` sibling does not need a mobile refresh signal (reclassify does not touch income — an assignable-bucket move cannot land in an Ingresos bucket, D-05's restriction). *Rejected:* optimistic client-side row-move (rollback state + re-grouping, disproportionate — backend is authoritative, refetch latency is acceptable, us-055 D-04 precedent).

7. **D-07 — Cross-bucket feedback via `AccessibilityInfo.announceForAccessibility` + a screen-owned status region, NOT a toast library.** Web uses a page-owned `role="status"` `aria-live` region («Movida a {ETIQUETA_BUCKET}.») that outlives the moved row (US-055 D-04). RN has no `aria-live`. The mobile idiom: on a confirmed cross-bucket move, call `AccessibilityInfo.announceForAccessibility('Movida a {ETIQUETA_BUCKET}.')` (the RN screen-reader announcement primitive) AND render a transient screen-owned status `Text` on `BucketDetalleScreen` (which outlives the row, exactly the us-055 "region survives the row's disappearance" requirement — the moved row unmounts on refetch). The confirmation itself is `Alert.alert` with the us-044 guard pattern (`useRef` in-flight lock + `cancelable: false`) carrying the money-move copy. The app has no toast primitive; this matches every existing mobile status surface. Message label uses the display map (`Deseos` → `Gustos`, `ETIQUETA_BUCKET` in `src/theme/colors.ts`). *Rejected:* a toast library (`yagni`, one line of feedback); a per-row inline announcement (unmounts with the row — the exact `ListaIngestas` bug class documented in-repo).

8. **D-08 — M2 (`/ingresos`) is read-only, CA-04 is M1-ONLY (web parity WDI-06).** User-confirmed. `IngresosMesPage`/`IngresosMesTable` on web explicitly ship NO reclassify (WDI-06). The mobile M2 screen renders header (period arrows via D-02, «Ingresos» title, `conteoLabel · totalLabel`, the static no-meta/no-semáforo note) and a `FlatList`/mapped rows of `Fecha · Descripción · Origen · Monto` — Origen as a small badge/`Text`, no `<table>` (RN has none). No reclassify control, no mutation, no refresh signal. *Rejected:* extending reclassify to income rows (breaks WDI-06 parity, adds scope the web deliberately excluded).

9. **D-09 — CA-05: jest-expo + RNTL per screen/component, plain unit tests per pure helper, RED-first (strict TDD active).** Pure functions (the two view-models, `aFechaCorta`, prev/next-month, the reclassify-target grouping) → plain jest unit tests. Screens/components → jest-expo + RNTL: the four fetch phases, legend-row navigation (assert `router.push` args), period-arrow stepping, group expand/collapse ("ver N más"), the reclassify `Modal` open/select/confirm flow with `Alert.alert` spied on its *arguments* (title + money-move lines + destructive confirm) and `announceForAccessibility` spied, and the refresh contract (assert refetch + `solicitarRecargaResumen` called on success). CLP amounts asserted string-safe. Maestro stays manual, out of CI (ADR-017).

## Out of scope

- **Any backend, endpoint, contract, or migration change.** `GET /api/buckets/{bucket}/detalle`, `GET /api/ingresos/mes`, `PATCH /api/transacciones/{id}/categoria` and their DTOs are correct and shipped (ADR-024: no business rule in the client). If this change needs a backend edit, the scope drifted.
- **Reclassify on M2 / income rows** (D-08, WDI-06 parity).
- **Bulk / multi-select reclassification** (#289/#290 non-goal).
- **Optimistic updates / row-move animation / undo** (D-06: refetch is authoritative).
- **Cross-type reclassify** (into an Ingresos/other-bucket category) — D-05 restricts the picker to `BUCKETS_ASIGNABLES`, mirroring US-055 D-02.
- **A new "Sin categoría" screen** — CA-01 routes SinCategoria to the same `/bucket/[bucket]` screen with `?destacar=sin-categoria`, reusing the destacado-group highlight; after a Sin-categoría row is classified, D-06's refetch drops it from the highlighted group.
- **Per-slice donut hit-testing** (D-01: the legend row is the target).
- **A bottom tab bar or nav chrome change** (out of scope in US-050 too; the legend rows + native stack back are the whole navigation).
- **TanStack Query / a caching layer on mobile** (D-03).
- **Web changes** — this is `apps/mobile` only.
