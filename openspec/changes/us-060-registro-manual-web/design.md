## 1. Overview

A new `/registrar` leaf route (thin container, exploration Approach A / product decision 1) renders a self-contained `RegistrarMovimientoForm`. The form is **type-first**: a `tipo` selector (Ingreso/Gasto) is the first control and drives the rest. The API layer adds one client fn + one response guard + one request-type alias + one mutation hook, mirroring the established JSON-body (non-multipart) never-throw doctrine. The nav gains one item.

```
routes/_authenticated/registrar.tsx   (thin container — reads esDemo, no logic)
  └─ RegistrarMovimientoForm  (stateful: form state machine on `tipo`, submit, feedback)
       ├─ useRegistrarMovimiento  → POST /api/movimientos, invalidate 4 dashboard keys (D-05)
       ├─ useCategorias           → catalog for the Gasto cascade (co-fetched, D-08)
       ├─ CampoTexto              → descripción (reused as-is; type='text')
       ├─ CampoSelect             → tipo, and (Gasto) bucket + categoría cascade
       └─ raw <label><input>      → fecha (type=date) + monto (type=text inputMode=numeric)
                                     (CampoTexto cannot host date/number — §0)
```

Design principles (ADR-024, SOLID, KISS, YAGNI, DRY): the client contributes **zero** business logic. The Ingreso auto-classification, the Gasto catalog/bucket validation, the money aggregation, and the `origen="Manual"` marker all come from the backend. Client-side pre-validation is **SHAPE** validation (is this a well-formed positive-integer string? a non-future date? a chosen bucket+categoría?), NOT a re-implementation of any business rule — the backend remains the sole authority and the client never classifies, never computes money, never derives a bucket. Spanish UI copy matching existing app strings; English identifiers/comments. No new npm deps; no new shadcn components; no `!` assertions (US-058/US-059 JD discipline).

## 3. Data flow

```
Mount
  RegistrarMovimientoForm renders (esDemo from route context, D-11/D-12)
    → useCategorias() fires (co-fetch, D-08) → CatalogoEstado derived
    → tipo state defaults 'Ingreso'; fecha defaults hoy = hoyLocal() (D-04; NOT aFechaCorta which slices UTC and yields TOMORROW for Chile evenings)

Type-first
  tipo CampoSelect → handleTipoChange(nuevo): setTipo + setBucketUI('') + setCategoriaId('')  [D-02 zeroing]
    tipo==='Ingreso' → render fecha/descripción/monto only
    tipo==='Gasto'   → additionally render bucket→categoría cascade  [D-08]
       + focus moves to the bucket select (tipo-keyed effect)         [D-09]

Gasto cascade
  bucket CampoSelect (options from catalogo.grupos + sentinel) → setBucketUI(v) + setCategoriaId('') [D-08 reset]
  categoría CampoSelect (options = chosen group's categorías + sentinel, disabled until bucketUI) → setCategoriaId(v)

Submit (handleEnviar)
  if (esDemo || mutation.isPending || isSubmittingRef.current) return  [D-10/D-11 belt-and-suspenders guard]
  pre-validate (SHAPE, not business rules):                           [D-02/D-03/D-04]
    descripcion !== ''
    esMontoManualValido(monto)  = esMontoStringValido && !startsWith('-') && !== '0'
    esFechaValida(fecha) && fecha <= hoyLocal()
    if tipo==='Gasto': bucketUI !== '' && categoriaId !== ''
    → on any failure: set field error(s) in the role="alert" region, RETURN (input NEVER cleared)  [CA-05]
  isSubmittingRef.current = true
  const body = construirBody()   // discriminated union; Ingreso arm has NO bucket/categoriaId  [D-01/D-07]
  mutation.mutate(body, {
    onSuccess: () => {  // 201                                        [D-10]
      clear form: fecha→hoyLocal(), descripcion→'', monto→'', bucketUI→'', categoriaId→'', tipo→'Ingreso'
      show inline confirmation in aria-live region
    },
    onError: (err) => {  // ApiError                                  [CA-05]
      show err.message in role="alert"; input PRESERVED (no clear)
    },
    onSettled: () => { isSubmittingRef.current = false },             [D-10]
  })

Success side-effects (in the hook, D-05)
  onSuccess invalidates ['resumen'],['resumen-anual'],['detalle-bucket-mes'],['ingresos-mes']
  → dashboard is already correct when the user clicks "Ir al dashboard" (static <a href="/">)
```

JSON-body POST to `/api/movimientos`; 400→`invalid` (fixed message, no body read), 401→`unauthorized`, non-2xx→`server`, network→`network`, 2xx guard-fail→`parse`. Validated by `esRegistrarMovimientoManualDto`.

## 5. No-`!` discipline

The response guard is a user-defined type predicate `value is RegistrarMovimientoManualDto`; `postMovimientoManual` returns `ApiResult<RegistrarMovimientoManualDto>`, so `mutation.data` (when defined) is fully typed — every read type-checks with zero `!`. The discriminated `RegistrarMovimientoManualInput` (D-07) means the Ingreso arm has no `bucket`/`categoriaId` key at the type level, so no assertion is ever needed to "drop" a field. This is the US-058/US-059 JD discipline designed in from the start.

## 8. ADR-024 boundary (non-negotiable)

The client contributes NO business logic. The Ingreso auto-classification, the Gasto catalog/bucket validation, the money aggregation, and the `origen="Manual"` marker all come from the backend. The UI only (a) collects the four type-first fields (+ the Gasto bucket/categoría), (b) SHAPE-validates them client-side (positive-integer string, non-future date, chosen bucket+categoría — none of which re-implements a business rule; the backend re-validates and is the authority), and (c) sends the correct discriminated-union variant. The bucket select is a UI navigation filter for the cascade; it DOES reach the wire for a Gasto (the backend requires it), but the client never DERIVES it — the user chooses it and the backend re-validates the (bucket, categoría) pairing. No client money math, no client Ingreso rule, no client classification.
