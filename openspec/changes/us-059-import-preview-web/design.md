## 1. Overview

Switch web `/subir` from the one-shot import to the US-057 **preview → review → commit** flow, entirely inside the existing `SubirCartola` state machine (exploration Approach A). The `File` stays in memory (a browser cannot re-read it from disk without a fresh user gesture), which is exactly what pins Approach A over B/C.

```
SubirCartola  (container — owns state machine, File, edits overlay, catalog fetch)
  ├─ usePreviewIngesta  → reads canonical data.filas / data.resumen
  ├─ useCommitIngesta   → NEW: POST /api/ingestas/commit (file + edits), invalidate + navigate '/'
  ├─ useCategorias      → catalog for the cascade (co-fetched, D-07)
  └─ PreviewMuestra  (presentational — resumen header + "nothing saved yet" + maps filas)
       └─ FilaRevision × N  (presentational row — cells + Duplicado badge + bucket→categoría cascade)
            └─ CampoSelect × 2 (existing native <select>)
```

Design principles (ADR-024, SOLID, KISS, YAGNI, DRY): the client contributes **zero** business logic — suggestions, dedup flags, `resumen` counts, and final classification all come from the backend; the UI renders backend-computed fields and collects a `categoriaId`-only overlay. No client money math, no client dedup, no Ingreso rule. Spanish UI copy matching existing app strings; English identifiers/comments. No new npm deps, no new shadcn components (D-09).

## 3. Data flow (preview → review → commit)

```
1. User picks file
   handleFileChange → validarArchivoWeb (client gate, unchanged)
     → reset previewMutation + commitMutation + edits(=empty Map)   [D-02]
     → previewMutation.mutate(file)                                  [estado: previsualizando]

2. Preview resolves
   previewIngesta → esPreviewIngestaDto (HARDENED, requires filas+resumen) [D-08]
     → data typed PreviewIngestaDtoConCanonicos (filas/resumen non-optional, NO `!`)
   estado: preview-listo → render <PreviewMuestra filas resumen edits onEditChange catalogo>

3. User edits classification (non-duplicate rows only)
   FilaRevision bucketUI select (UI filter)  → narrows categoría options   [D-06]
   FilaRevision categoría select             → onEditChange(rowIndex, categoriaId|null)
     → SubirCartola: edits.set(rowIndex, value) (new Map)                   [D-03]
   Display value per row = edits.has(i) ? edits.get(i) : fila.sugerido?.categoriaId ?? null  [D-05]

4a. "Agregar transacciones"
   handleConfirmar (double-submit guard) → commitMutation.mutate(
       { file, edits: Array.from(edits, ([rowIndex,categoriaId]) => ({rowIndex,categoriaId})) },  [D-03/D-04]
       { onSuccess: () => navigate({ to: '/' }) })                          [D-05 call-site nav]
   estado: committing → (201) onSuccess invalidates resumen/anual/detalle/ingestas + navigate '/'  [D-05]

4b. "Descartar"
   handleDescartar → reset file + edits + both mutations → navigate({ to: '/' })  [D-02, CA-05]

ERROR (preview)
   estado: preview-error → role="alert" shows backend-scrubbed message  [D-11]
     retry path A: re-pick file (input re-enabled) → step 1 (resets mutation + edits)

ERROR (commit)
   estado: error → role="alert" shows backend-scrubbed message; review table REMAINS rendered with edits intact  [D-11]
     retry path A: "Agregar transacciones" re-enabled → step 4a (same file + same overlay, no reset)
     retry path B: re-pick file (input re-enabled) → step 1 (handleFileChange resets both mutations + edits)
     retry path C: "Descartar" → step 4b (resets all state, navigates '/')
```

## 5. Non-null narrowing (no `!`) — how TS flows

```
previewIngesta(): Promise<ApiResult<PreviewIngestaDtoConCanonicos>>       // D-08 return type
   where PreviewIngestaDtoConCanonicos =
     Omit<PreviewIngestaDto, 'filas'|'resumen'> & {
       filas: ReadonlyArray<PreviewFilaDto>;                              // NonNullable
       resumen: NonNullable<PreviewIngestaDto['resumen']>;
     }
esPreviewIngestaDto(value): value is PreviewIngestaDtoConCanonicos        // user-defined type predicate
```
`usePreviewIngesta` is re-typed `useMutation<PreviewIngestaDtoConCanonicos, ApiError, File>`, so `previewMutation.data` (when defined) has `filas`/`resumen` as required — every read (`data.filas.map`, `data.resumen.totalFilas`) type-checks with **zero `!`**. This is the mechanism US-058's JD demanded: the guard and the type narrow together at the boundary.

## 9. ADR-024 boundary (non-negotiable)

The client contributes NO business logic: suggested classification, duplicate flags, `resumen` counts, and final persisted classification all come from the backend. The UI only (a) renders backend-computed fields (amounts as strings, never re-computed) and (b) collects the `categoriaId`-only overlay (D-03/D-06). The bucket select is a UI navigation filter that never reaches the wire. No client money math, no client dedup, no client Ingreso rule.
