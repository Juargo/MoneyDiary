## 1. Overview + Design Principles

Split the one-shot `POST /api/ingestas` into **preview → review/edit → commit**. Preview writes
nothing; commit is the only writer. The commit mechanism is **stateless re-upload + edits overlay**
(proposal §1): the client re-sends the previewed file plus a JSON `edits` overlay, the server
re-parses (stays authoritative on money/parse/dedup) and applies the overlay over auto-classification.

```
POST /api/ingestas/preview   (multipart: file)                         [NO WRITE — by construction]
  └─ routes/ingesta.routes.ts :: registrarIngestas (preview handler)   (infra, closure-DI)
       │   forwards req.userId! (OVERRIDES the prior "NO forwarda userId" comment — see D-08/D-12)
       └─ PreviewIngestaUseCase.execute({fileReader, userId})          (application, Result<T,E>)
            ├─ EjecutarPipelineIngestaUseCase (SHARED front, third caller) → {banco, estructura, transacciones, nombreArchivo}
            ├─ IAccountReader.findByBanco(userId, banco) → accountId|null   (read-only port; D-05)
            │    null ⇒ all esDuplicado=false, no dedup query (D-06)
            ├─ rangoFechas + ITransaccionExistenteReader.buscarPorCuentaYRango (decrypts descripcion; D-17)
            ├─ marcarDuplicados(existentes, transacciones) → boolean[] (standalone helper; D-07)
            └─ CategorizarTransaccionUseCase per row  (patterns via ICatalogoClasificacion; SinCategoria→null; D-09)
       └─ aPreviewIngestaDto(...)   (infra, BigInt→string, per-row rowIndex/esDuplicado/sugerido)

POST /api/ingestas/commit    (multipart: file + edits JSON)            [ONLY WRITER]
  └─ routes/ingesta.routes.ts :: registrarIngestas (commit handler)    (infra, closure-DI)
       │   uses subirArchivoConEdits() — own multer instance with fieldSize: 256 KB (D-02)
       ├─ parse+validate `edits` field → CommitEdit[]                  (infra boundary, D-03)
       └─ CommitIngestaUseCase.execute({fileReader, userId, edits})    (application, Result<T,E>)
            ├─ shared front pipeline → {banco, estructura, transacciones, nombreArchivo}  (D-16)
            ├─ IAccountRepository.ensure(...)                    ←WRITE (called by CommitIngestaUseCase
            │                                                           OUTSIDE the extracted front; D-01/7b)
            ├─ DetectarDuplicadosUseCase (against current DB)          [CA-03]
            ├─ ICategoriaRepository.listarConPatrones(userId) — REQUIRED (membership + bucket map; D-10/D-15)
            ├─ ICatalogoClasificacion.findAll(userId) — REQUIRED (patterns for auto-classify; D-10)
            │      either load fails ⇒ commit fails, persists nothing (fail-closed)
            ├─ validate ALL overlay rowIndex in range [0, filas.length) (D-04) → 400 if any out-of-range
            ├─ validate overlay categoriaId ∈ listarConPatrones id set (D-10) → 400
            ├─ categorizar per row (auto-classification, in-memory)    [D-11, PRE-PERSIST]
            ├─ apply overlay; bucket from Map<categoriaId,Bucket>      [D-11/D-15]
            │    → builds TransaccionAPersistir[]: {transaccion, bucket: Bucket|null, categoriaId}
            │    → aPersistencia (infra) resolves Bucket→FK via BUCKET_IDS [D-15/9b]
            └─ PersistTransactionsUseCase.execute(TransaccionAPersistir[]) → persistirProcesada
                                                                       [SINGLE WRITE, atomic, US-004; D-11]
       └─ CommitIngestaResult → aCommitIngestaResponseDto              (infra; D-13, §5.2b)
            (in-memory transacciones[] from pre-persist rows; §5.2b)
            (CommitTransaccionResponseDto carries bucket:string + categoriaId; D-13)
```

Design principles (ADR-005/011/015/024): dependency rule untouched (`domain ← application ←
infrastructure`); `Result<T,E>` never throws in domain/application; Spanish naming in
domain/application, English in infra; money stays `bigint` internally and is emitted as BigInt-safe
strings at the HTTP boundary; amounts scrubbed from every error message; multi-tenant WHERE by
`userId` (RNF-SEC-006); strict TDD (ADR-016), application before infrastructure. **No schema
migration** (stateless commit). `web`/`mobile` untouched (US-059/US-061 consume this later).

## 2. Decisions (ADR-style)

| id | decision | rationale | rejected alternative |
|----|----------|-----------|----------------------|
| **D-01** | **Commit is a NEW sibling `CommitIngestaUseCase`, not a refactored `ProcessIngestaUseCase` + overlay param.** The one shared source of truth is the parse chain `ingest→detect→validate→normalize`, extracted to a small **`EjecutarPipelineIngestaUseCase`** that `ProcessIngestaUseCase`, `CommitIngestaUseCase`, AND `PreviewIngestaUseCase` (the third caller — preview-ingesta.use-case.ts:112-160 today has its own duplicate xlsx/pdf branch) all call. **`ensure()` is explicitly OUTSIDE the extracted front**: `ProcessIngestaUseCase` and `CommitIngestaUseCase` each call `IAccountRepository.ensure()` themselves after the shared pipeline returns; `PreviewIngestaUseCase` calls the read-only `IAccountReader.findByBanco()` instead (D-05). The shared front returns `{banco, estructura, transacciones, nombreArchivo}` (D-16) or the shared error union — it knows nothing about accounts or dedup. `estructura` is needed by `ProcessIngestaUseCase` for its post-persist response discrimination (process-ingesta.use-case.ts:289-298) and `totalFilasDatos` is needed by preview for the `resumen` counts. The overlay + persist + categorization orchestration stays per-use-case. | **Read the code first (proposal Q3):** `ProcessIngestaUseCase.runPipeline` (process-ingesta.use-case.ts:182-329) is a 150-line linear method whose tail (`persist → runCategorizacion` with the try/catch island, the FALLIDA single-writer boundary in `execute`, the estructura-resumen discrimination) is one-shot-specific. Threading an `overlay?` param through it would fork every downstream step behind a flag — a YAGNI-flag anti-pattern and a KISS regression on the most sensitive money path. Extracting only the **front** (detect→normalize, genuinely identical across all three callers) gives DRY where it matters. `ProcessIngestaUseCase` behaviour is byte-for-byte preserved (regression guard). Pinning `ensure()` outside the extracted front preserves ISP: the shared module has no write-port dependency (SRP: one reason to change). | (a) Refactor `ProcessIngestaUseCase` to take `overlay?` — forks the hot path behind a flag, risks the one-shot regression guard. (b) Duplicate the whole pipeline in commit — violates the "one source of truth" constraint (proposal §6). (c) Include `ensure()` in the extracted front — forces a write-port dependency into the shared module, breaking the preview no-write guarantee and widening the front's responsibility. |
| **D-02** | **`edits` multipart field (proposal Q1): field name `edits`, a single UTF-8 JSON string in a text part of the SAME `multipart/form-data` request as `file`.** JSON shape: `Array<{ rowIndex: number, categoriaId: string \| null }>`. **Size cap 256 KB** on the raw text field (enforced by multer `limits.fieldSize`). Absent/empty `edits` ⇒ empty overlay (commit with zero edits is valid — pure auto-classification, the one-shot behaviour). **Multer shape pinned: commit uses its OWN multer instance via a NEW helper `subirArchivoConEdits()`** in the same routes module, distinct from the shared `subirArchivo()` (ingesta.routes.ts:161-165). `subirArchivoConEdits()` calls `.single('file')` with `limits: { fileSize: MAX_FILE_SIZE, fieldSize: 256 * 1024 }`. The shared `subirArchivo()` is NOT modified — it keeps only `fileSize` and is used by the one-shot and preview routes. The `fieldSize` default of multer (1 MB) is too large to serve as the edits cap and the shared helper must not silently grow to carry the commit-specific limit. **No switch to `.fields()`**. | `subirArchivo()` sets only `limits.fileSize`; multer's `fieldSize` default is 1 MB — too loose for edits. Giving commit its own helper (`subirArchivoConEdits()`) keeps the shared path unchanged (zero regression risk) and makes the per-field cap explicit and reviewable. 256 KB ≈ 4000 edit entries at ~64 B each — comfortably above any real cartola. JSON-in-a-text-part is the ONE shape that deviates from the existing route pattern — pinned here (proposal §1, risk "unusual shape"). | (a) A second endpoint taking JSON-only after a preview handle — needs server-side staging (rejected in proposal §1). (b) base64 the edits into a header — opaque, size-limited by proxies. (c) No cap — memory-abuse surface on financial infra. (d) Widening `subirArchivo()` to add `fieldSize` — changes shared behavior under one-shot and preview routes silently. |
| **D-03** | **Malformed `edits` ⇒ descriptive HTTP 400, amounts scrubbed, via a NEW domain error `EdicionesInvalidasError` (application/domain boundary).** Malformed = not valid JSON, not an array, an element missing `rowIndex`/`categoriaId`, `rowIndex` not a non-negative integer, or `categoriaId` not `string\|null`. The route parses+shape-validates `edits` at the infra boundary BEFORE calling the use case; a shape failure short-circuits to 400. The message names WHAT is wrong (`"el campo edits no es un JSON válido"`, `"cada edición requiere rowIndex entero y categoriaId"`) and **never echoes the raw field** (could carry a pasted amount). | Mirrors the repo's boundary-validation discipline (catalogo `.safeParse` → scrubbed 400, `perfil` D-09). Parsing at the infra boundary keeps the application use case receiving a typed `CommitEdit[]`, never a raw string (ISP: the use case doesn't know about JSON/multipart). | Parsing `edits` inside the use case (leaks transport concern into application, breaks ADR-005). |
| **D-04** | **Stale/out-of-range `rowIndex` ⇒ CONFIRM the proposal: descriptive HTTP 400, fail-closed, whole commit rejected (`RowIndexFueraDeRangoError`).** **The valid range is the PRE-dedup normalized set** — i.e. `[0, filas.length)` where `filas` is the full re-parsed/normalized row set (the same set `PreviewFilaResult` addresses, D-08), BEFORE any duplicate is omitted. Validation happens AFTER re-parse+normalize and BEFORE dedup-driven omission touches indices: any overlay `rowIndex` outside `[0, filas.length)` ⇒ 400 `"una edición referencia una fila que no existe en el archivo (el archivo pudo haber cambiado)"`. Duplicate `rowIndex` in the overlay ⇒ also 400 (ambiguous intent). **An in-range `rowIndex` whose row is later omitted as a commit-time duplicate is NOT an error** — it is silently dropped (D-11a); only OUT-OF-range (or duplicate-in-overlay) indices 400 here. `rowIndex` addresses the pre-dedup set precisely so preview (which shows all rows, including duplicates) and the overlay agree on identity. | **Reasoning (proposal Q2):** an out-of-range index means the file the user committed is NOT the file they previewed (re-parse yields a different row count/order). Silently ignoring the entry would persist rows the user believes they reclassified — a **money-integrity** failure worse than a rejected upload. Fail-closed is the conservative default the whole codebase already uses (dedup aborts the pipeline when it can't verify; `NoOpCryptoService` fail-safe). The user re-previews and re-commits — cheap, stateless, no data risk. In-range indices are validated deterministically because the server re-parses the same bytes (normalization is pure per bank strategy). | (a) Per-entry ignore of stale indices (proposal's alternative) — silently drops the user's intent, reclassifies nothing while reporting success, breaks the review contract. (b) Best-effort partial apply — non-deterministic which edits land. |
| **D-05** | **NEW read-only account port `IAccountReader.findByBanco(userId, banco: DetectedBank) → Result<{ accountId: string } \| null, PersistenciaFallidaError>`.** `null` when the user never imported from this (banco, tipoCuenta, numeroCuenta). Prisma adapter `PrismaAccountReader` does a `findUnique` on the SAME natural key as `ensure()` — `userId_banco_tipoCuenta_numeroCuentaBlindIndex` — computing `numeroCuentaBlindIndex` via the injected `IBlindIndexService` (`normalizeNumeroCuenta` + `blindIndex.compute`, verbatim from `PrismaAccountRepository`). **No upsert, no `create` branch — read-only by construction.** | The Account natural key includes `numeroCuentaBlindIndex` (prisma-account.repository.ts:44-52), so a `findByBanco` that scopes dedup to the RIGHT account MUST compute the blind index — passing the full `DetectedBank` (which carries `numeroCuenta`) is the minimum. Returning `null` (not creating) is what preserves the no-write guarantee: no account ⇒ no prior transactions ⇒ `DetectarDuplicados` runs with `accountId=""`/skips the reader ⇒ 0 dups, 0 writes. Small port, one method, one Prisma call (ISP/SOLID: read-only sibling of `IAccountRepository`, NOT a widening of it). | (a) Adding a `find` method to `IAccountRepository` — widens a write port, a preview holding it could reach `ensure()` (the top risk, proposal Risks). (b) Making `ensure()` optionally read-only via a flag — a two-mode write port, worse. |
| **D-06** | **Preview's dedup call when `findByBanco` returns `null`: SHORT-CIRCUIT to `{esDuplicado:false}` for every row without calling `DetectarDuplicadosUseCase`.** `DetectarDuplicadosInput.accountId` is a non-empty account id in every existing caller; rather than invent a sentinel `accountId=""`, preview checks `accountId === null` and returns "all new" directly (the use case's own empty-batch guard already returns 0 dups, but here the batch is non-empty and there's simply no account to query). | Keeps `DetectarDuplicadosUseCase` and `ITransaccionExistenteReader` **unchanged** (no null-accountId contract to add) — preview owns the "no account yet" branch. Matches the use case's conservative contract (it only ever queries a real account). | Passing `accountId=""` to the reader — an empty-string WHERE is a latent cross-account/empty-result footgun; better to not query at all. |
| **D-07** | **Preview needs per-row dedup status, but `DetectarDuplicadosUseCase` returns `{nuevas, duplicadas: count}` — it does NOT tag each row.** Full preview dedup flow (verified against detectar-duplicados.use-case.ts): **(1)** `IAccountReader.findByBanco(userId, banco) → accountId \| null` (D-05); **(2)** if `null` ⇒ short-circuit, every row `esDuplicado: false`, no reader query (D-06); **(3)** if a real `accountId`, compute the `[fechaDesde, fechaHasta]` range over the incoming `transacciones` (min/max of `tx.fecha`, one pass); **(4)** `ITransaccionExistenteReader.buscarPorCuentaYRango(accountId, fechaDesde, fechaHasta)` → decrypted existing rows (D-17); **(5)** the pure helper `marcarDuplicados(existentes, transacciones): boolean[]` builds a `Set<clave>` over `existentes` via `construirClaveDuplicado` and returns a per-row boolean mask preserving order. **The fecha-range computation is EXTRACTED to a shared pure helper `rangoFechas(transacciones): {desde, hasta}`** (co-located in the same `marcar-duplicados.helper.ts` module) and reused by BOTH `marcarDuplicados`' callers and `DetectarDuplicadosUseCase` — the range logic currently inlined at detectar-duplicados.use-case.ts:59-63 is replaced by a call to `rangoFechas` so there is ONE definition (DRY: the range is a shared derivation, not duplicated). `marcarDuplicados` is a standalone pure function co-located in its own module under `application/use-cases/` (NOT a method on `DetectarDuplicadosUseCase` — no new class, no use-case widening); it receives the pre-fetched `existentes` (the preview use case owns the `ITransaccionExistenteReader` call and passes results in). `DetectarDuplicadosUseCase` is left single-method and single-purpose (still returns count semantics for commit); it is refactored ONLY to call `rangoFechas` and share `construirClaveDuplicado`. Commit keeps using `DetectarDuplicadosUseCase.execute`. | `DetectarDuplicadosUseCase` already partitions preserving order (detectar-duplicados.use-case.ts:87-101); the per-row boolean is the same computation viewed row-wise. One shared clave-construction path AND one shared range path (DRY at the knowledge that matters — the natural key and the query bound), two projections (partition for commit, boolean mask for preview). Extracting `rangoFechas` closes the duplication the two-round review flagged: without it, the range would be computed once in `DetectarDuplicadosUseCase` and again in the preview path. | (a) Adding `marcarDuplicados` as a second method on `DetectarDuplicadosUseCase` — widens a single-purpose use case for a second caller (ISP violation). (b) Re-deriving the dedup key OR the fecha range in the DTO mapper / preview inline — duplicates natural-key/range knowledge (DRY violation on a security-relevant rule). (c) Widening `DetectarDuplicadosResult` with per-row tags and having commit ignore them — YAGNI for commit. |
| **D-08** | **`PreviewIngestaResult`/`PreviewIngestaDto` extension (proposal §3):** result grows `resumen: {totalFilas, duplicadosDetectados, nuevas}` + `filas: PreviewFilaResult[]` (was `muestra`), each row `{ rowIndex, fecha, descripcion, cargo, abono, esDuplicado, sugerido: {bucket, categoriaId} \| null }`. `rowIndex` = position in the full normalized set (0-based). **`PREVIEW_SAMPLE_MAX = 50` cap REMOVED for this flow (decision 1)** — `filas` is ALL rows. `muestra` → `filas` is a rename in both the result type and the DTO. | `rowIndex` is the contract tying preview to the commit overlay (proposal §3); it addresses the full set so a stale index is detectable (D-04). `sugerido` comes from `CategorizarTransaccionUseCase` over the caller's catalog (`ICatalogoClasificacion.findAll(userId)`), `null` when no pattern matches AND not Ingreso — same semantics as the pipeline's degradable island (non-Ingreso rows may stay unclassified). Money stays string (BigInt-safe). | Keeping a capped `muestra` — cannot drive a real review screen (proposal §Why now). |
| **D-08a** | **Compat shim (product decision 2026-08-21): the preview reshape is ADDITIVE, not a rename.** The response carries BOTH shapes until US-061 removes them alongside the one-shot: CANONICAL `resumen` + `filas` (full set, per-row dedup/suggestion) AND deprecated LEGACY `estructura: {totalFilasDatos}` + `muestra[]` (first 50 rows, old 4-field shape `{fecha, descripcion, cargo, abono}` only). `estructura.totalFilasDatos === resumen.totalFilas`. The legacy view is a PURE PROJECTION derived in `aPreviewIngestaDto` — the use case is untouched. In the zod schema (and thus the generated `@moneydiary/api-client` type) `resumen`/`filas` are marked `.optional()` and `estructura`/`muestra` required, ONLY so legacy client literals (deployed mobile APK, pre-migration web/mobile) stay assignable; the server ALWAYS emits all four. | A response consumed by SHIPPED clients (the deployed mobile APK calls preview and cannot be updated by repo code; web/mobile depend on `@moneydiary/api-client` and still read `estructura`/`muestra`) cannot be reshaped in a breaking way without migrating those clients first. CI's cross-workspace typecheck (api-client type changes fan out to the web + mobile jobs) is the tripwire that caught the breaking rename. Additive compat keeps every shipped consumer green with ZERO changes under `apps/web`/`apps/mobile` until the client-migration US lands. | (a) Breaking rename `muestra`→`filas` (original PR2) — broke the deployed APK and failed web+mobile typecheck. (b) A second `/preview/v2` endpoint — needless surface for a transitional shape. |
| **D-09** | **`sugerido.bucket` + `sugerido.categoriaId` mapping.** `CategorizarTransaccionUseCase.execute` returns `{categoria: {id,nombre}\|null, bucket: Bucket}` and ALWAYS returns `Result.ok` (verified: categorizar-transaccion.use-case.ts:52-91 — `Result<…, never>`, never fails). Preview maps its result to the DTO's `sugerido` by ACTIVELY inspecting the `bucket`: when `bucket === Bucket.SinCategoria` ⇒ `sugerido: null` (no classification available); when `bucket === Bucket.Ingreso` ⇒ `{bucket: 'Ingreso', categoriaId: null}`; otherwise (a pattern matched) ⇒ `{bucket: <enum string>, categoriaId: categoria!.id}`. **The DTO `bucket` strings are the serialized `Bucket` enum values verified in code (bucket.ts:11-17): `'Necesidades' \| 'Deseos' \| 'Ahorro' \| 'Ingreso' \| 'SinCategoria'`** — the enum's `string` values ARE its member values, so `String(bucket)` / direct assignment yields those exact tokens. The TS shape is `{ bucket: string, categoriaId: string \| null } \| null`. **`SinCategoria` is NOT emitted as a `sugerido` payload** — the mapper detects it (`bucket === Bucket.SinCategoria`) and maps to `sugerido: null`; the preview vocabulary is `{bucket, categoriaId}` when classified and `null` when unclassified. The spec (PREV-EXT-01) was aligned to this exact shape; backend states the classification and the client must not re-derive the Ingreso rule (ADR-024). If the catalog load FAILS at preview, degrade on preview's own terms: run with `patrones=[]` so the Ingreso rule still classifies (Ingreso ⇒ `{bucket:'Ingreso', categoriaId:null}`), the rest resolve to `Bucket.SinCategoria` ⇒ `sugerido: null` (catalog down, suggestions unavailable for non-Ingreso rows; same rendered meaning as no-match). Never crash preview with a 500 on a catalog blip (CA-04). This degradation is stated independently of `runCategorizacion`'s catalog-down branch (which leaves non-Ingreso rows as DB `null` pending a retry — a different semantics, a different state). | Reuses the EXACT classification path (DRY on the categorization rule — proposal CA-01). Pinning the enum's string values against bucket.ts removes the ambiguity the review flagged; the active `SinCategoria`-detection is what keeps the boundary clean since `CategorizarTransaccionUseCase` cannot signal "unclassified" any other way (it always returns ok with a bucket). | Re-implementing classification for the suggestion (DRY violation — the preview would LIE). Passing `SinCategoria` through as a `sugerido` — it is a post-persist bucket state, not a preview vocabulary item; the mapper actively demotes it to `null`. Hardcoding bucket strings not tied to the enum — would drift from `Bucket`. |
| **D-10** | **Cross-tenant `categoriaId` validation (proposal §4, RNF-SEC-006) happens IN `CommitIngestaUseCase` (application), BEFORE persist, against the caller's OWN category-id set from `ICategoriaRepository.listarConPatrones(userId)` (NOT `ICatalogoClasificacion.findAll`, see D-15). Both catalog loads are REQUIRED at commit — if either fails, the commit fails entirely (fail-closed).** `CommitIngestaUseCase` loads the caller's categories ONCE (via `listarConPatrones`) and the caller's patterns ONCE (via `findAll`) before persist. Every overlay `categoriaId` (non-null) must be a member of the `listarConPatrones` category-id set — this is the AUTHORITATIVE membership set because it includes pattern-less own categories that `findAll` would miss (verified: prisma-catalogo-clasificacion.repository.ts:36 queries only `patronClasificacion`). A `categoriaId` not in the set ⇒ `CategoriaFueraDeCatalogoError` ⇒ scrubbed 400, whole commit rejected (fail-closed, like D-04). `null` categoriaId is always valid (explicit un-classification). **If EITHER load fails (infra error, `CategorizacionFallidaError` from `findAll` or a thrown `listarConPatrones` wrapped into `PersistenciaFallidaError` by the use case's try/catch — see D-18 for the complete `CommitIngestaError` union and the error-to-HTTP mapping), the commit fails with a descriptive error (amounts scrubbed), persists NOTHING, and the client can retry.** `CommitIngestaUseCase.execute` mirrors the outer try/catch structure of `ProcessIngestaUseCase.execute` (process-ingesta.use-case.ts:122-143): a top-level `try/catch` translates any mid-flight throw (from adapters or collaborators) into `Result.fail(PersistenciaFallidaError)` so that NO exception ever escapes the use case boundary. Rationale: the cross-tenant validation cannot run without the category list, and it is security-mandatory (RNF-SEC-006). The degradable island is a one-shot semantic (an ongoing ingesta survives a catalog blip by leaving rows `null` pending retry); commit is an explicit, retryable user action, and persisting without validation would be a security regression. This deliberately does NOT copy the existing post-persist `runCategorizacion` structure from `ProcessIngestaUseCase`; that island stays one-shot-only. | Cross-tenant validation cannot run without the category list — skipping persist-anyway would bypass RNF-SEC-006. Using `findAll` (patterns-only) for membership would falsely reject a user's own pattern-less category (false 400) — `listarConPatrones` is the only complete own-category source. Commit is idempotent on the client side (retry = re-upload the same file + same edits); fail-closed is the safe default for the money path. | Using `findAll` for membership (misses pattern-less categories — false cross-tenant rejection); validating in the Prisma writer (too late, deep; leaks the security rule into infra); trusting the id and letting a FK error surface (leaks DB structure); persisting on catalog failure without validation (security regression). |
| **D-11** | **Overlay application: overlay is applied IN-MEMORY BEFORE the single `persistirProcesada` call. `TransaccionAPersistir` threads the full persistence chain (repository port → `PersistTransactionsUseCase` → `ProcessIngestaUseCase`/`CommitIngestaUseCase`).** The algorithm for `CommitIngestaUseCase` is: (1) parse/normalize → `Transaccion[]`; (2) dedup → omit duplicates, count; (3) load catalog via `ICatalogoClasificacion.findAll(userId)` — REQUIRED (fail-closed per D-10; if `findAll` fails, commit fails entirely, persists nothing, client retries); **(3a) validate ALL overlay `rowIndex` values are in range `[0, filas.length)` (D-04) BEFORE classification begins — any out-of-range ⇒ 400, nothing persisted;** (4) validate overlay categoriaId ⊆ catalog (D-10) → 400 if any fails; type: BigInt cargo/abono → string (BigInt-safe), `bucket` enum → string, `categoriaId` passthrough.

`categoriaId: string | null`.

## 8. Risks carried into apply

- **Preview silently regains write capability** (top risk): mitigated by read-only port types + `crearPreviewIngesta` wiring only read adapters + the no-write unit AND integration tests (D-12). The reviewer signal MOVED from "crear takes no prisma" to "crear wires only readers + the no-write test" — apply MUST keep that test as the guardrail. **The no-write composition test is MANDATORY-BLOCKING** (§7).
- **Pipeline extraction drift** (D-01): the one-shot regression guard test is the pin; extract only the genuinely-identical front, leave the one-shot tail untouched.
- **`numeroCuentaBlindIndex` mismatch**: `findByBanco` MUST use the SAME `normalizeNumeroCuenta` + blind index derivation as `ensure()`, else preview dedup scopes to the wrong (or no) account. Covered by an integration test that previews after a real import and sees the duplicates.
- **`edits` multipart shape**: unusual; pinned by D-02/D-03 + the schema + `parseEdits` unit tests.
- **Persistence-chain re-typing touches the one-shot money path** (D-11/8a/9/9a/9b/9c): `PersistTransactionsUseCase` + `IIngestaRepository` + the mapper are shared by the LIVE one-shot. Mitigation: one-shot passes `{transaccion, bucket:null, categoriaId:null}` at the application boundary; `aPersistencia` resolves `null → bucketId:null` (byte-for-byte identical persisted result), pinned by the two-level regression guard (unit + integration; §7 TDD constraint b) + integration assertion that `Transaccion.bucketId`/`categoriaId` columns stay null. Keep `TransaccionPersistencia` scalar-only to avoid the spread-leak hazard (Fix 2).
- **Bucket FK vs enum confusion** (D-15): `Transaccion.bucketId` is a FK to `BucketPresupuesto`, not the enum. `TransaccionAPersistir.bucket` carries the domain enum; `aPersistencia` resolves via the SINGLE `BUCKET_IDS` map in the adapter. A test asserts the persisted `Transaccion.bucketId` column is a physical id (`'bucket-*'`), never an enum string like `'Necesidades'`.
- **Dedup silently never matches under encryption** (D-17): if the existente reader is wired WITHOUT `crypto` (or a future refactor drops the decrypt), every preview/commit dedup key mismatches and `esDuplicado`/omission always yields "new". Mitigation: D-17 pins the decrypt as load-bearing; the dedup integration test (preview after a real import sees the duplicates) catches a regression.
- **Membership set completeness** (D-10/D-15): using patterns-only `findAll` for cross-tenant validation would falsely reject a user's pattern-less own category. Mitigation: `listarConPatrones` (all own categories) is the membership + bucket-map source; a unit test accepts a pattern-less own category.
